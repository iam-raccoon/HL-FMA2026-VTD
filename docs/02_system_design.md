## 2.1 전체 구성

```
[주행 전 · 개발PC/제어PC]                               [주행 중 · 제어PC ↔ VTD PC]
 주최측 좌표 CSV ─▶ vtd/plan_route.py ─▶ routes/<코스>.json        9910 DataPacket 1109B
 xodr 지도 ──────┬▶ vtd/build_lane_plan.py ─▶ <코스>_lane.json ─┐        │
                 ├▶ vtd/build_tl_map.py ─▶ tl_map_livinglab.json ├─▶ src/main.py ─▶ src/drive.py
                 ├▶ vtd/build_crosswalk_map.py ─▶ crosswalks.json│        │   (경로 투영 → 추월 FSM
                 └▶ vtd/build_stoplines.py ─▶ stoplines.json ────┘        │    → 행동 → 조향·종방향)
 eval/check_route.py 로 경로를 달리기 전에 검사                    9910 CtrlPacket 9B ◀─┘
```

### 2.1.1 제어PC에서 도는 코드 — `src/`

대회 당일 제어PC에서 실제로 도는 코드다. `main.py` 는 입출력만 맡고, 어떻게 달릴지는 전부 `drive.py` 에 있어
소켓 없이 `State` 하나만 넣어 테스트할 수 있다.

| 파일 | 역할 |
|---|---|
| `main.py` | 진입점 — CLI · VTD 연결 · 수신 루프 · 제어 송신 · 로깅 · 종료 |
| `netcfg.py` | VTD 주소 — 제어PC 자기 IP 로 대회망(192.168.50.x)을 자동 판별, `VTD_HOST` 로 덮어쓰기 |
| `drive.py` | 주행 판단·제어 스택(State → Command). 경로 최근접점 → 목표속도 → 객체 경로 투영 → 추월 FSM → 행동 → 조향·종방향 |
| `vtd_io.py` | 9910 프로토콜(1109B 파싱 / 9B 송신) + 속도 추정 + 리스폰 감지 + 객체 분류(`is_vru`, `classify_object`) |
| `behavior.py` | 도로교통법 판단 — 신호 / 보행자 / 앞차 ACC / 장애물 / 끼어들기 / 근접 통과 |
| `overtake.py` | 추월 상태기계(FOLLOW → WAIT → PASS → RETURN). **차(최대변 ≥ 1.2 m)만** 담당하고, 그보다 작은 연료통·라바콘은 `drive.py` 의 nudge(횡회피)가 맡는다 |
| `control.py` | Pure Pursuit(횡) + 2-pass 속도 프로파일 + 종방향 PI(제동 비대칭) |
| `route_frame.py` | 객체를 경로에 투영해 차선 판정(곡선 오판 방지) + `offset_path` |
| `scenario.py` | 경로 / 신호 정지선 / 보호구역 JSON 로더 |
| `run_logger.py` | 주행 CSV 기록(채점·정지선 매핑 입력, 매 프레임 flush) |
| `experimental/avoidance.py` | (미사용) 옛 lattice 회피 — 차선 경계를 몰라 인도 이탈을 일으켜 격리 보관. [2.9](#29-실험-브랜치--frenet-lattice)의 lattice 와는 **다른 구현**이다 |

## 2.2 인터페이스 — VTD 와 주고받는 것

VTD 와는 **raw TCP/UDP/RTSP** 로만 통신한다. ROS1/ROS2 는 쓰지 않고, 주최측의 C++ RDB 모듈(GCC8 필요)도 쓰지 않는다 —
9910 규격을 파이썬으로 직접 구현했다(`libHLVTD.so` 실측).

### 2.2.1 9910 패킷

| 방향 | 패킷 | 구성 |
|---|---|---|
| 받기 | **DataPacket 1109B** TCP | ego `X,Y,Z,heading,pitch,roll`(6×f32) + `objects[30]`(각 36B: id u32 + x,y,z,heading,speed,length,width,height 8×f32) + trafficLight(id i32 + state u8). LE, 헤더 없음 |
| 보내기 | **CtrlPacket 9B** TCP | `steering[rad] f32` + `targetAccel[m/s²] f32` + `turnSignal u8` |

⚠️ **9910 은 단일 클라이언트다** — 주행 중 다른 프로그램이 접속하면 제어가 끊긴다.

### 2.2.2 패킷에 없는 것과 그 대응

| 없는 것·함정 | 대응 |
|---|---|
| **비상등** — `turnSignal` 은 0/1/2 만 받는다 | 나머지 값은 전부 소등으로 뭉개진다(아래 디스어셈블). 정차 중 표시는 **우측 지시등 유지**(`GOAL_STOP_SIG`, 기본 2) |
| **ego 속도** — 객체만 speed 필드가 있다 | 위치 미분. 위치는 sim 클럭으로 전진하는데 시간은 벽시계로 재서 흔들린다 → **0.3초 창 이동거리/걸린시간** + 가벼운 EMA |
| **객체 종류** | 치수로 추론([2.5](#25-객체-분류--치수로-추론한다)) |
| **차선 정보** | 지도에서 미리 계산한 차로계획(`routes/<코스>_lane.json` — 공식 v1~v6 은 `routes/lane_plan_v1_v6.json`, `vtd/build_lane_plan.py`)([2.3](#23-지도에서-읽는-것--노면표시)) |
| **정지선** | 지도에서 뽑은 신호·횡단보도·고아 정지선 DB |
| ego 기준점 = **뒷축 중심**(`egoReferencePoint=rear_axle_center`) | 정지선 여유 계산에 앞범퍼 3.81m 보정 |

**지시등.** 추측이 아니라 플러그인 디스어셈블로 확인했다(2026-08-28, `libHLVTD.so.1.0.0`):

```asm
ControlApplier::mapTurnSignalFlags(unsigned char):
    mov eax,1 ; cmp dil,1 ; je ret                    ; ts==1 -> 1 (좌)
    xor eax,eax ; cmp dil,2 ; sete al ; add eax,eax   ; ts==2 -> 2 (우), 그 외 0
```

실측으로도 3 을 정차 82프레임 동안 보냈지만 화면에 아무것도 안 켜졌다(CSV `sig=3`).

**속도 추정.** 타임스탬프 필드가 없고 패킷이 뭉쳐 오면 한 프레임이 0.020s 만에 도착해 16.9m/s 로 읽힌다(참값 8.3).
0.3초 창으로 바꾼 뒤 실주행에서 프레임간 변동 0.52→**0.15 km/h**, v3 최고속도 33.7→**30.9 km/h**(속도위반 프레임 2→0).

**차로계획.** 지정차로(회전 차로) · 중앙선 점선 여부 · 차로별 여유 · 경로 자체의 차선변경(지시등용)이 들어 있다.
이 코스는 좌여유 3.5m 이상이 45%뿐이고 우여유는 100%, 중앙선 점선은 7%다. 교차로 안은 연결도로가 겹쳐
계산이 불가능한 곳이 있어 **모름**으로 두고, 모르는 곳에서는 앞지르기를 시작하지 않는다(도교법 제22조와도 일치).

**리스폰.** 경로이탈 0.5s 면 정상 차선으로 순간이동하고 **건당 감점**이다. 좌표 점프만 보면 놓친다 — 실측된 리스폰은
**1.59m 이동 + 헤딩 20° 스냅(≈250°/s)** 이었다. 그래서 감지는 `순간이동 OR 불가능한 요레이트(>3 rad/s)` 두 조건을 모두 본다.

**VTD Traffic 모듈.** 연속 주행하면 죽는다. 그러면 주변 차량이 전부 `v=0.0` 인데 프로세스는 멀쩡해 보인다 —
검증할 땐 몇 판마다 VTD 를 재시작한다([2.9.3](#293-vtd-한-판)).

## 2.3 지도에서 읽는 것 — 노면표시

9910 패킷에는 차로도, 제한속도도, 지정차로도 없다. 전부 xodr 의 **노면표시 오브젝트**에서 읽는다. 이 맵은
`<type><speed>` 도 속도 표지판도 선언하지 않아서, 바닥에 그려진 것이 유일한 근거다(채점자와 사람이 실제로 보는 것도 그것이다).

| 오브젝트 | 개수 | 뜻 | 쓰는 곳 |
|---|---|---|---|
| `RM_537_ST/LT/RT` | 458/144/134 | 직진 / 좌회전 / 우회전 | 지정차로 |
| `RM_538_SLT/SRT` | 97/168 | 직진+좌 / 직진+우 | 지정차로 |
| `RM_539_LUT/UT` | 68/5 | 좌회전+유턴 / 유턴 | 지정차로 |
| `RM_517_50` | 69 | 속도제한 50 | 제한속도 |
| `roadmark_speed_30` | 71 | 속도제한 30 | 제한속도 |
| `RM_536` | 62 | **어린이보호구역** | 제한속도 30 |
| `RM_518` | 77 | **보호구역 속도제한** | 제한속도 30 |

### 2.3.1 지정차로는 화살표로 판정한다

junction 의 `laneLink` 는 '물리적으로 이어지는가'만 말한다. road 310 lane -1 은 직진 연결로가 **있어서** laneLink 상
직진이 되지만 바닥엔 `RM_537_LT`(좌회전 전용)가 그려져 있다 — 실주행에서 그대로 좌회전 차로로 직진했고 화면에 바로
보였다. 그래서 **화살표가 있으면 화살표가 이긴다**(9경유지 교차로 33곳 중 30곳에서 화살표가 읽힌다). 화살표가 없는
곳에서만 `laneLink` 로 떨어진다. 이 판정을 경로 계획에 어떻게 넣는지는 [2.4.5](#245-지정차로는-탐색-그래프-안에서-지킨다).

차로 **번호**로 묶지 않는다 — `laneSection` 마다 번호가 재부여되므로(road 128 은 7구간) 같은 물리 차로가 다른 번호가
된다. **도로 `t` 좌표**로 경로와 직접 맞춘다(화살표는 차로 한가운데 그려지므로 `t` 가 곧 그 차로의 중심).

### 2.3.2 맵의 화살표가 자기모순인 곳

남은 화살표 경고 3건은 **고칠 대상이 아니다** — 화살표를 지킬 방법이 물리적으로 없다.

| 도로 | 모순 |
|---|---|
| road 310 lane -1 | 좌회전 전용으로 칠해져 있는데 그 차로의 연결로는 809(직진) 하나뿐 |
| road 396 lane -1 | 좌회전 전용인데 lane -2 는 574(우회전 전용)라 직진할 차로가 거기밖에 없다 |
| road 190 | 편도 1차로 — 주행차로가 좌우 하나씩인데 바닥엔 좌회전 화살표만 있고, junction 10 은 같은 차로에서 우회전·좌회전 연결로를 **둘 다** 건다 |

맵의 화살표가 빠진 것이지 경로가 틀린 게 아니다 — 경고만 남기고 그냥 간다.

### 2.3.3 보호구역 제한속도

⚠️ **보호구역을 `roadmark_speed_30` 로만 찾으면 놓친다.** `RM_536`(어린이보호구역)이 그려진 도로 17개 중 **16개에
`roadmark_speed_30` 이 없다**. 이걸 빠뜨려서 9경유지에서 보호구역 **419m 를 50km/h 로 통과**했다(s=1987\~2528m 의
연속 스쿨존 7개 도로 + s=3386\~3432m). 보호구역은 어린이·노인·장애인 불문 30km/h 라 `RM_518` 에 숫자가 안 붙어
있어도 30 으로 읽는다. 표시가 **없는** 도로(대부분 교차로 연결로)는 '제한 없음'이 아니라 **직전 값 유지**이고,
도로망 다익스트라로 전파한다(`road_speed_limits_net`).

## 2.4 차로 단위 경로 계획

내비게이션과 같은 문제(**lane-level route planning**)이고, 업계가 수렴한 구조도 같다.
[Lanelet2](https://dl.acm.org/doi/10.1109/ITSC.2018.8569929) 의 `routing::RoutingGraph` 가 하는 일 — **차로를 노드로,
이음/차선변경을 간선으로 두고 최단경로** — 을 OpenDRIVE 위에서 직접 구현했다(`vtd/plan_route.py`). Lanelet2 처럼
그래프를 미리 굽지 않고 xodr 에서 매번 만든다. OpenDRIVE 기성품으로는 [esmini](https://github.com/esmini/esmini) 의
RoadManager 가 가장 가깝지만 경로탐색 API 가 문서화돼 있지 않고 C++ 를 붙여야 해서, 실주행 검증이 끝난 자체 구현을 쓴다.

```
노드 = (road, lane, 그 도로에서의 차선변경 횟수) + 몇 번째 경유지까지 지났는지
간선 = xodr 이 명시한 lane link / junction laneLink   비용 = 도로 길이
     + 같은 도로 안 차선변경                          비용 = 활주로 기반(2.4.6)
```

| 설계 결정 | 이유(실측) |
|---|---|
| 경유지는 탐색 상태에 넣는다(층 그래프) | 구간마다 따로 풀면 이음매에서 59.6m 벌어지고 169° 유턴 |
| 출발만 차로를 고정하고 경유지·종점은 반경으로 연다 | 경유지를 못박으면 108m 직선이 695m, 9경유지 코스가 2km → 5.4km |
| 방향은 차로 번호 부호로 | 기하로 추측한 첫 버전은 리스폰 81건·완주 실패 |
| 계획한 차로를 차로계획에 그대로 넘긴다 | 교차로 '모름' 604점 → 0점 |
| 지정차로는 탐색 그래프에서 지킨다 | 오프셋으로 때우면 리스폰 1 → 3 |
| 차선변경 비용은 활주로에 반비례 | 고정 60m 는 400m 직선과 출구 20m 앞을 같은 값으로 봤다 |
| 동점은 늦게 바꾸는 쪽 | 힙 순서만 바뀌어 600m 를 한 차로 바깥으로 도는 경로가 나왔다 |
| 차선변경은 끝낼 시간을 주고 시작 | 옛 램프는 50km/h 에서 2초뿐 |

### 2.4.1 경유지는 탐색 상태에 넣는다

구간마다 따로 계산해 기하를 이어붙이면 이음매에서 **59.6m 벌어지고 169° 유턴**이 생긴다 — 경유지는 도로 중간 점이라
탐색을 새로 시작하면 **반대 방향 차로로 도착/출발**할 수 있기 때문이다. 도착 차로를 그대로 넘겨주는 것도 안 된다(하필
막다른 차로면 그냥 '경로 없음'). 층을 두면 알아서 우회한다.

### 2.4.2 출발만 차로를 고정한다

**경유지는 차로를 못박지 않는다(반경 6m 안의 차로 전부).** 왕복도로에서 점 하나를 '담는' 차로는 한 방향뿐이라, 강제하면
반대로 접근하려고 한 바퀴 돈다(직선 108m 구간이 695m, 9경유지 코스가 2km → 5.4km). 주최측도 도착 판정을 반경
10~20m 로 본다.

**출발점만 차로를 고정한다** — 차는 이미 그 차로에 놓여 있다(`StartLane`). 거기까지 반경으로 열면 계획이 **옆 차로에서
시작**해 VTD 가 경로 이탈로 본다(실측: 검증본 대비 중앙값 3.3m = 한 차로 통째로 밀림).

**종점은 엄격 판정을 먼저 쓰고, 실패할 때만 반경 6m 로 넓힌다.** 예전엔 종점도 고정했는데, 2026-09-03 사전테스트
경로 2 에서 종점을 담는 차로가 하나뿐이라 계획이 통째로 실패했다. 경위: [부록 A](99_dev_log.md).

### 2.4.3 방향은 차로 번호 부호로 정한다

방향은 추측하지 않는다 — **우측통행에서 차로 번호 부호가 곧 진행 방향**이다(음수 = s 증가). 도로 단위로 짰던 첫
버전은 이음매마다 방향을 기하로 추측하다 뒤집혀 **리스폰 81건·완주 실패**했다.

### 2.4.4 계획 결과를 차로계획에 그대로 넘긴다

경로점마다 `(도로, 차로, s, t)` 를 같이 내보내면(`ego_lanes`) `build_lane_plan` 이 지도에서 되찾을 필요가 없다 —
교차로처럼 연결로가 겹쳐 되찾기가 불가능한 곳도 채워진다(모름 604점 → **0점**). 이게 없을 때는 교차로에서 앞이
막혀도 **옆 차선이 비어 있는지조차 몰라** 계속 기다렸다.

교차로 점에는 `j:1` 을 달아 **앞지르기는 계속 금지**한다(도교법 제22조). 금지되는 건 '앞지르기'지 '같은 방향
진로변경'이 아니므로 장애물 회피 차선변경은 된다.

### 2.4.5 지정차로는 탐색 그래프 안에서 지킨다

처음엔 계획을 다 짠 뒤 "옆 차로로 2.85m 비켜라"(`need`)로 고쳤는데, 차가 실제로 옮긴 **직후 VTD 가 경로이탈로
리스폰**시켰다(9경유지 s=644m 에서 2건 연속, 리스폰 1 → 3). 시나리오가 ego 경로를 `StartLane` 으로 못박고 VTD 는
시나리오 Path 를 기준으로 이탈을 보므로, **차로를 통째로 옮기는 건 경로가 할 일**이다. 이 스택에서 가장 비싸게 배운 것이다.

지금은 화살표가 금지하는 회전에 `ARROW_VIOLATION`(500m) 페널티를 걸어 탐색이 알아서 옳은 차로로 간다. 차선변경
비용과 같이 **끊지는 않는다** — 끊으면 '경로 없음'이 된다. `build_lane_plan` 의 `need` 는 `NEED_MAX`(1.2m) 이하,
즉 **차로 안 미세보정에만** 쓴다.

| 9경유지 코스 | 오프셋으로 때움 | 탐색에서 지킴 |
|---|---|---|
| 경로 길이 | 3488m | 3322m |
| 지정차로 `need` | 182점 | **0점** |
| 리스폰 | 3 | **0**(v1·v3·9경유지 전부) |

### 2.4.6 차선변경 비용 — 활주로에 반비례

[arXiv:2206.02883 (Lane-Level Route Planning for Autonomous Vehicles)](https://arxiv.org/abs/2206.02883) 이 지적하듯
차선변경은 공짜인 결정적 연산이 아니라 **확률적으로 실패할 수 있는 행동**이다(논문은 MDP 로 모델링해 Dijkstra 유사
방법으로 O(n log n) 에 푼다). 처음엔 **고정 60m** 페널티였는데, 400m 직선에서 한 칸 옮기는 것과 출구 20m 앞에서
옮기는 것이 같은 값이었다. `1회당 활주로 = 도로길이 / 변경횟수`, 필요량 45m(30km/h 에서 5.4초) 기준으로 비용을 키운다.

| 도로 길이 | 1회 | 2회 | 3회 |
|---|---|---|---|
| 168m | 60 | 60 | 60 |
| 60m | 60 | 90 | 135 |
| 30m | 90 | 180 | 240 |
| 10m | 240 | 240 | 240 |

활주로가 모자라도 **간선을 끊지는 않는다**(상한 4배). 끊으면 그 길밖에 없는 코스에서 '경로 없음'이 된다. 비싸게만
만들어 *가능하면* 긴 도로에서 미리 옮기게 한다.

### 2.4.7 동점은 최대한 늦게 바꾸는 쪽으로 깬다

차선변경 1회를 어느 도로에서 하든 거리 합이 같아 **비용이 정확히 동점인 경로가 흔하다**(실측: 두 경로 모두 974.11m).
노드에 변경횟수를 추가한 것만으로 힙 순서가 바뀌어, 600m 를 **한 차로 바깥으로 도는** 경로가 튀어나왔다(녹화 대비
편차 0.80m → 3.20m). 그래서 2순위 키로 **변경 지점의 주행거리 합을 최대화**한다 — 사람도 내비도 좌회전 차로에
600m 전부터 들어가 있지 않는다. 2순위라서 활주로 페널티를 뒤집지 못한다.

녹화본 대비 편차는 **진단용이지 합격 기준이 아니다.** 계획 경로가 앞 460m 구간에서 녹화본과 중앙값 3.18m 떨어져
있는데도 실주행 리스폰은 0 이었다(2026-08-16). VTD 의 이탈 판정 기준은 녹화한 리더차 궤적이 아니라 시나리오 자체의
Path 다. 편차가 크면 "차로 선택이 달라졌다"는 신호로만 보고, 판정은 실주행으로 한다.

### 2.4.8 차선변경은 끝낼 시간을 주고 시작한다

두 군데를 같이 고쳐야 했다.

| 어디 | 전 | 후 |
|---|---|---|
| `build_lane_plan` 의 `need` 램프 | 70m 전 시작 → 28m 전 100%(50km/h 면 2초) | **110m 시작 / 45m 전 완료**(65m = 4.7초), `LANE_RATE` 0.6 → 0.9m/s(한 차로 3.6초) |
| `plan_route.sample_lane` 의 경로 기하 | 보간이 도로 끝(rem=0)에서 완료 — road 2003 은 마지막 2m 를 도로 끝 9.8m 남기고 | `lc_blend()` 로 **`LC_FINISH`(20m) 남기고 완료** — 9경유지에서 가장 늦은 완료 지점 9.8m → **29.4m** 전 |

⚠️ 활주로가 짧으면 여유도 그만큼만 뗀다(40% 상한). 그냥 20m 를 빼면 분모가 0 에 가까워져 한 스텝에 0→1 로
튄다 — v7 경로에서 헤딩 64° 반전이 났었다.

## 2.5 객체 분류 — 치수로 추론한다

9910 패킷에는 **타입 필드가 없다**(id · x · y · z · heading · speed · length · width · height 뿐). 그래서 **치수로 추론**한다.
판정 함수는 `vtd_io.is_vru()` **하나뿐이다** — 예전엔 `behavior.py` · `overtake.py` · `drive.py` 에 복사돼 있었고, 주석에
"한쪽만 바뀌면 모순" 이라고 적어두고도 실제로 어긋났다. 주행 정책은 `classify_object()` 가 네 종류로 가른다.

| 분류 | 조건 | 대응 |
|---|---|---|
| VRU(취약대상) | `is_vru()` — 아래 규칙 | 사람과 같은 옆 여유 1.2m, 양보 |

### 2.5.2 판정 규칙

취약 도로이용자는 키를 낮추고, **기둥은 앞뒤 길이로 뺀다**:

```python
if length < 0.20:            return False   # 표지판 0.04 · 폴 0.05 · 삽 0.06
if height >= 1.2:            return max(L,W) < 1.2 or (W <= 1.0 and L <= 3.0)
if height >= 0.85:           return W <= 0.70 and L <= 2.30   # 휠체어·자전거
```

`L ≥ 0.20` 이 핵심이다 — **사람은 아무리 말라도 앞뒤 0.234m**(DummyPerson)인데 기둥은 0.04~0.11m 다. 취약자 문턱
0.85 는 기름통(0.61)보다 0.24m 위라 2026-08-14 의 '콘을 사람으로 보고 영구정지' 는 재발하지 않는다. 겹치는 사물
7종은 치수 시그니처로 제외하고 `moose` 는 취약대상에 포함한다. 40 km/h(`VRU_MAX_SPEED`)보다 빠르면 치수와 상관없이
차량(이륜차)으로 본다. `tests/test_person_class.py` 가 카탈로그 222종을 실제로 읽어 전수 검증한다.

전수 검사에서 드러나 고친 구멍은 셋이다.

| 무엇 | 실측 | 왜 |
|---|---|---|
| **휠체어·자전거를 사람으로 안 봤다** | 휠체어 20m 앞에서 `FOLLOW` 3.6km/h — 옆여유를 사람용 1.2m 가 아니라 **차량용 0.35m** 로 뒀다 | 문턱이 `H≥1.2` 인데 휠체어 0.92 · 자전거 1.10 이다 |
| **길가 표지판을 사람으로 봤다** | 갓길 3.0m·4.0m 표지판에 `PED_STILL_ASIDE` **18km/h** — 노선 표지판마다 깎였다 | 표지판 0.04×0.60×2.10 이 `W≤1.0 · L≤3.0 · H≥1.2` 를 통과 |
| `overtake._is_ped` 가 높이를 안 봤다 | 포트홀·노면패치 **56종**이 사람 | 죽은 코드였지만 다음 사람이 쓰면 바로 사고 — 삭제 |

## 2.6 판단 — 행동층

`behavior.py` 는 우선순위 중재기다 — 긴급정지(임박충돌) > 보행자 양보 > 적신호 정지 > 앞차 ACC(안전거리) >
장애물 정지 > 차선유지. 규칙마다 속도 상한을 내고 **가장 낮은 값이 이긴다.** 실제로 속도를 잡은 규칙은 CSV 의
`cap_by` 칸에 남는다(`reason` 과 다를 수 있다). 인지는 9910 `objects[30]` GT 를 그대로 쓴다(라이다/YOLO 불필요).

### 2.6.2 회피와 추월

| | 사물 회피(nudge) | 추월 FSM |
|---|---|---|
| 대상 | 최대변 < 1.2m(`NUDGE_MAX_DIM`) — 연료통·라바콘 | 최대변 ≥ 1.2m — 서거나 느린 차 |
| 코드 | `drive.py` `_nudge_offset` | `overtake.py` `Overtaker` + `drive.py` |
| 동작 | 옆 차로가 통째로 비면 차로 하나를 온전히 옮긴다(상한 `NUDGE_MAX` 3.8m) | FOLLOW → WAIT(뒤에 정지·대기) → PASS(옆 차로 주행) → RETURN(복귀) |
| 넘어갈 쪽 | `_side_for` — 같은 방향 차로의 좌우 여유(`l`/`r`) | 같은 함수로 좌우를 각각 물어 **실제로 빈 쪽**을 고른다(필요 폭 = 차로폭 + 차폭 절반 0.943m) |

기본 모드는 중앙선 너머를 회피 공간으로 쓰지 않는다. `ALLOW_CENTERLINE_ESCAPE=1` 을 명시한 실험 모드만 오래 갇혔을 때
반대차선까지 쓴다 — 평가상 중앙선 침범이며 면책되지 않는다([1.5](01_problem.md#15-주최측이-확정해-준-해석)).

## 2.7 제어

`drive.py` 가 매 프레임 한 번 돈다: 경로 최근접점 → 목표속도 → 객체를 경로 기준으로 투영 → 추월 FSM → 행동(도교법) →
추월 중 속도제한 → 무한정지 탈출 → 조향(Pure Pursuit) + 종방향 PI.

| 단 | 방식(`control.py`) | 주요 값 |
|---|---|---|
| 횡 | Pure Pursuit — lookahead = clamp(lmin + k·v, lmin, lmax) | 축거 2.95m · k 0.5 · lookahead 4~20m · 조향 한계 35° |
| 목표속도 | 2-pass 곡률 속도 프로파일(`speed_profile_2pass`) + 제한속도 반영(`apply_speed_limits`) | a_lat 3.0 · 가속 1.5 · 감속 3.0 m/s² · 차로계획 제한속도 앞 감속 1.2 m/s² |
| 종방향 | PI(적분 anti-windup, `LongPI`) — **제동 게인을 가속보다 크게** | kp 0.8 · 제동 kp 2.5 · ki 0.25 · 출력 −5.0~+2.0 m/s² |

## 2.8 알려진 한계 — 좌회전 차로를 못 잡는 곳

"가끔씩 좌회전 차선에서 직진하는 경우가 있다"는 지적을 `check_route ⑨` 로 세어 보면 **전체 9개 경로 중 4곳**이다(코스 A 1 ·
코스 E 1 · WP9 2, 2026-08-20 진단). 두 종류다.

| 종류 | 곳 | 처리 |
|---|---|---|
| 맵 모순 — 그 회전을 허용하는 차로가 없다 | 코스 A `road 2264`, WP9 `road 396`·`road 190` | 고칠 수 없다. **벌점만 물고 지나간다** |
| 라우터 버그 — laneSection 재번호 | 코스 E `road 2814` | **아직 안 고쳤다** |

`check_route ⑨` 는 위반마다 두 경우를 자동으로 가른다 — 같은 연결로로 들어가는 다른 진출 차로 중 **그 회전을 허용하는
화살표가 그려진 차로가 실재하는가**. 당일에 필요한 건 "손댈 수 있나 없나"다.

```
코스 A  road 2264 lane -1 {좌회전,직진} 인데 우회전   (맵 모순: 그 회전을 허용하는 차로가 없다)
WP9    road  396 lane -1 {좌회전}      인데 직진     (맵 모순)
WP9    road  190 lane +1 {좌회전}      인데 우회전   (맵 모순)
코스 E  road 2814 lane +3 {직진}        인데 좌회전   ← **lane +2 로 갔어야 한다**
```

### 2.8.1 맵 모순

`road 2264` 는 우리 방향 차로가 **-1 하나뿐**인데 그 화살표가 `{좌회전,직진}` 이고 코스는 **우회전**을 요구한다. 지킬
차로가 존재하지 않는다. WP9 의 2곳도 같다(`road 396`·`road 190`, [2.3.2](#232-맵의-화살표가-자기모순인-곳)).
`build_lane_plan` 도 독립적으로 같은 경고를 찍는다.

### 2.8.2 laneSection 재번호

`road 2814` 는 laneSection 이 **3개**(s=0 / 72.6 / 75.9)이고 **같은 물리 차로의 번호가 구간마다 다르다.** 우리가 달린
자리는 t≈4.7 로 처음부터 끝까지 같은데:

```
진입(s=190, 섹션 75.9)   lane +2   t=4.777    <- 라우터가 고른 '차로 2'
진출(s=  4, 섹션 0   )   lane +3   t=4.628    <- 화살표가 있는 자리. {직진}
```

섹션 s=0 에만 **`type=none` 폭 0.47m 짜리 lane 1**(차로 사이 틈)이 끼어 있어 번호가 한 칸 밀린다.

| 섹션 s=0 기준 | 폭 | 중심 t | 화살표 |
|---|---|---|---|
| lane 1 (`type=none`) | 0.47 | 0.24 | — |
| **lane 2** | 2.65 | **1.80** | **{좌회전,유턴}** ← 여기로 갔어야 |
| lane 3 | 3.07 | 4.66 | {직진} ← 우리가 간 곳 |
| lane 4 | 2.94 | 6.66 | {직진,우회전} |

**라우터는 "차로 2"를 골랐다고 믿지만, 그 2 는 진입 섹션의 2 이고 물리적으로는 진출 섹션의 3 이다.** 연결로 3099 는
진출 기준 lane 2 도 받아준다(`laneLink from=2`) — **길은 있는데 번호 때문에 못 찾아간다.** 좌회전 포켓은 진입 구간에
대응 차로가 없어서, 포켓 간선이 넣는 진출 번호 `2` 가 물리적으로 다른 진입 번호 2 와 겹쳐 중복 방지 조건
(`same_ex[j] not in here`)에 걸려 간선이 사라진다. **노드의 차로 번호가 '진입 구간 기준'이라는 규약 자체가 이 경우를
표현하지 못한다.**

벌점(`ARROW_VIOLATION` 500 → 3000)·경유지 추가·연결로 직행 간선은 모두 안 통했다 — 앞의 둘은 경로만 길어지고 위반은
그대로였고, 마지막은 전 코스를 망가뜨려 되돌렸다. 제대로 고치려면 **노드의 차로 식별자를 물리적으로 유일한 것**(진출번호 +
포켓 표식, 또는 `t` 좌표)으로 바꿔야 하는데, `successors`·`thru`·`arrow_moves`·`sample_lane`·`save` 를 다 건드리고
**전 코스 재검증까지 묶어서** 해야 하는 일이다. 당일에 ⑨ 가 "맞는 차로가 실재한다"로 뜨면 그 회전 하나는 벌점을 안고
간다. 경위(시도한 것과 수치): [부록 A](99_dev_log.md).

## 2.9 실험 브랜치 — Frenet lattice

**대회 코드(`main`)에는 lattice 가 없다.** `src/lattice.py` 와 `--lattice` 옵션은 `test_lattice` 브랜치에만 있고, 거기서도
**기본값이 `off`** 라 대회 경로는 바뀌지 않는다.

lattice 는 **"어디로 비킬지"를 정하지 않는다.** 그건 추월 FSM · nudge · Behavior 가 도교법에 맞춰 이미 정한다. lattice 는
**그 목표까지 가는 곡선만** 차로 경계 안에서 그리고, 안전한 후보가 하나도 없으면 검증된 기존 경로로 그대로 떨어진다.

| 브랜치 | 내용 |
|---|---|
| `main` | 대회용. lattice 없음 |
| `test_lattice` | `main` + lattice. 그대로는 못 쓰는 세 곳을 고쳐서 합쳤다(`1e6eb8b`) |
| `experiment-frenet-lattice` | 친구가 올린 **2026-08-27 원본 스냅샷**. 이후 수정 16건이 빠져 있어, 그대로 달리면 고친 결함이 되살아난다 — 비교는 `test_lattice` 에서 `off` ↔ `active` 로 |

| 모드 | 조향 | 계산 | 쓰는 곳 |
|---|---|---|---|
| `off` | 기존 FSM | 안 함 | **대회 기본값** |
| `shadow` | 기존 FSM | 매 프레임 | 진단 전용. `lat_applied` 는 항상 0 |
| `active` | 후보 있으면 lattice | 횡기동 중에만 | 실험. 후보 없으면 자동 fallback |

**판단 — 대회는 `off` 로 간다.**

- 오프라인 22판 중 FSM 이 실제로 횡기동한 판은 **6판뿐**이고, 그 6판은 **이미 100점**이다. lattice 가 올려줄 점수가 남아 있지 않다.
- 실제 코스는 더 심하다 — 코스 A 756초 완주, 코스 E 주행에서 **기동 0회**.
- VTD 채점은 접촉·신호·속도·정지선·리스폰을 본다. **곡선의 매끄러움은 항목에 없다.**
- 지금 `active` 를 켜면 차선변경마다 **35km/h 로 감속**한다. 비용함수에 속도항이 없어 10km/h 든 60km/h 든 항상 24m
  종단거리를 고르는데, 그 곡률이면 `a_lat ≤ 3.0` 상한이 34.7km/h 다. 32m 를 골랐으면 46km/h 였고 cost 차이는 0.055 뿐이다.
- VTD 실주행 active 회귀와 공식 18판 active 는 아직 안 했다.

### 2.9.1 `lat=IDLE` 은 고장이 아니다

`active` 는 FSM 이 **실제로 횡기동 중일 때만**(추월 PASS·RETURN, nudge |off| > 0.05, WAIT 중 오프셋 차 > 0.20m) 조향을 넘겨받는다.
그래서 한 판 내내 `lat=IDLE/0` 이 정상인 판이 있다(2026-08-30: 코스 A 756초 완주, 코스 E 전 프레임 IDLE). 로그의 `off` 칸이
계속 `+0.0` 이면 기동이 0회였다는 뜻이다. 경로에 이미 들어 있는 차선변경은 lattice 가 안 건드리고, `NARROW_BLOCK` 은 오히려
nudge 를 0 으로 만든다. 그래서 `shadow` 는 게이트를 무시하고 매 프레임 돈다. 경위: [부록 A](99_dev_log.md).

### 2.9.2 콘솔 읽는 법

로그 줄 끝의 `lat=<상태><*>/<후보수>`.

| 표시 | 뜻 |
|---|---|
| `lat=OFF/0` | `LATTICE=off`. 계산 자체를 안 한다 |
| `lat=IDLE/0` | 켜져 있지만 부를 일이 없었다(위). `shadow` 에서는 안 나온다 |
| `lat=OK/17` | 후보 17개 중 하나를 골랐다 |
| `lat=NO_FEASIBLE/0` | 안전한 후보가 없다 → 기존 FSM 경로로 fallback |
| `lat=NO_CORRIDOR` | **진짜 교차로**(`jx=1`) 안 |
| `lat=NO_LANE_PLAN` | 차로계획이 없다 |

`*` 는 FSM 이 실제로 횡기동 중이었다는 뜻이다(`lat=OK*/17`). reason 에 `+LAT` 가 붙으면 그 프레임 조향이 실제로 lattice
경로에서 나왔다.
